# OpenGarden Webapp

Org-side admin UI for the OpenGarden protocol. Built on Payload 3 + Next.js 16 + SQLite, and the first consumer of the [`@refi-italia/opengarden`](../../packages/sdk) SDK.

This package owns the **authoring and lifecycle layer** for the protocol: registering areas, scheduling interventions, recording crew field data, validating, and producing evidence bundles. It does **not** yet own the SDK-calling layer that mints attestations on chain — collections store fields that mirror chain state, but populating them is the responsibility of server actions that will land in a follow-up plan.

## Quick start

```bash
# 1. Install workspace dependencies (run from repo root)
pnpm install

# 2. Build the SDK so its dist/ exists for the webapp to consume
pnpm --filter @refi-italia/opengarden build

# 3. Seed env values
cp .env.example .env
# .env must set DATABASE_URL, PAYLOAD_SECRET, PROTOCOL_CHAIN,
# OPENGARDEN_SIGNER_PRIVATE_KEY, OPENGARDEN_RPC_URL, and CRON_SECRET.

# 4. Create an admin user (idempotent — re-running upgrades roles)
ADMIN_EMAIL=you@example.com \
ADMIN_PASSWORD=changeme \
ADMIN_DISPLAY_NAME='You' \
pnpm --filter webapp seed:admin

# 5. Start the dev server
pnpm --filter webapp dev
# → http://localhost:3000/admin/login
```

The SQLite adapter pushes the schema automatically on first boot in dev, so there is no migration step. To start over from a clean DB, delete `apps/webapp/webapp.db` and rerun `seed:admin`.

## Data model overview

| Group | Members | Role |
|---|---|---|
| **Registry** | `sponsors`, `staff`, `gardeners`, `areas` | Stable reference data. `sponsors` and `staff` carry hashable identifiers that freeze on first use to keep on-chain `commissionRef` / `validatorId` derivations idempotent. |
| **Lifecycle** | `interventions`, `gardenerCheckins/Checkouts/Reports`, `adminValidations`, `healthchecks` | Day-to-day operational rows. `interventions` is a state machine (`draft → scheduled → in_progress → validated → published`, plus `revoked` / `failed` branches). |
| **Settlement** | `evidenceBundles`, `chainTransactions` | Read-mostly. `evidenceBundles` has its own build state machine (`draft → built → uploaded → published → verified`); `chainTransactions` is an append-only audit log of every SDK call. |
| **System** | `users`, `media`, `organizationProfile`, `taskCatalog` | Auth + configuration. Runtime chain config lives in `PROTOCOL_CHAIN` (env) and the SDK's chain constants — no persistent global. |

### Lifecycle and freeze guarantees

- **Lifecycle status fields are server-action only.** The intervention and evidence-bundle state machines are enforced by `beforeChange` hooks (`validateInterventionTransition`, `enforceEvidenceBundleState`) that reject any edge not in the documented transition tables. Form-based saves cannot drive transitions; they always go through a server action that passes `req.context.skipLifecycleHooks: true`. This guarantees `Save` on the admin form can never accidentally mint an attestation.
- **Stage groups are read-only after their stage.** A `beforeValidate` hook on `interventions` silently resets any form-level write to `scheduling.*` / `validation.*` / `execution.*` / `revocation.*` back to its original value (server actions still write through the bypass). Defense-in-depth against direct REST writes.
- **Hash inputs freeze on first use.** Once a `sponsors` or `staff` row is referenced from a scheduled-or-later intervention, `frozen: true` is flipped and `freezeOnFirstUse` rejects any update that would change the canonical hash. Display-only fields stay editable.
- **No SDK chain calls in hooks.** Every hook is a pure derivation (hash compute) or a pure validity guard (transition table). All side effects — chain calls, cross-collection writes, `chain.*` mirror population — live in server action handlers (deferred to a follow-up plan), not in collection hooks.

### Operator flow: bootstrapping the chain

Chain selection is an env var (`PROTOCOL_CHAIN`); addresses and canonical schema UIDs come from the SDK's chain constants. There is no persistent `protocolConfig` global and no manual-paste step.

To bring up a new chain:

1. Set `PROTOCOL_CHAIN` in `.env` to one of the supported names (`celo-mainnet`, `celo-alfajores`, `optimism-mainnet`, `optimism-sepolia`, `base-mainnet`, `base-sepolia`).
2. If the SDK already ships schema UIDs for that chain (see `packages/sdk/src/chains/schemas.json`), you're done — `getOpenGardenContext` resolves them from the chain constant at task runtime.
3. If the chain isn't in `schemas.json` yet, register + name the schemas once from a workstation with a funded signer:
   ```bash
   OPENGARDEN_TEST_CHAIN=<chain-name> \
   OPENGARDEN_TEST_PRIVATE_KEY=<your-key> \
   OPENGARDEN_TEST_RPC_URL=<rpc> \
   pnpm --filter @refi-italia/opengarden register-schemas
   pnpm --filter @refi-italia/opengarden name-schemas
   ```
   The scripts persist the UIDs into `schemas.json`. Commit the diff and redeploy the webapp against the updated SDK.

**Chain-switch safety.** The webapp refuses to boot (at the first `getOpenGardenContext` call) if `chainTransactions` already contains activity against a different `chainId` than the one `PROTOCOL_CHAIN` currently resolves to. Redeploying with the wrong chain set will fail loudly before any new on-chain writes corrupt the audit trail.

## Tests

Integration specs live in `tests/int/*.int.spec.ts` and exercise the data model via Payload's Local API:

- `sponsorHash.int.spec.ts` — sponsor canonical-hash determinism vs the SDK helper.
- `freezeSemantics.int.spec.ts` — frozen sponsors refuse hash-input edits but accept display edits; partial-unique enforcement on non-volunteer sponsors.
- `accessControl.int.spec.ts` — every role attempts create on representative collections; allowed/denied outcomes match the role matrix.
- `referentialIntegrity.int.spec.ts` — full intervention chain (area → intervention → crew → checkins/checkouts/reports → validation) round-trips through the Local API.
- `lifecycleTransitions.int.spec.ts` — every legal and illegal edge in the intervention and evidence-bundle state machines.

Vitest is configured to run the integration suite in a single forked process with shared module graph and serialized files (`pool: { type: 'forks', singleFork: true }`, `isolate: false`, `fileParallelism: false`). Payload's SQLite schema push is not idempotent across processes and the SQLite file allows only one writer, so this is required.

## Chain calls via the jobs queue

All SDK-calling side effects run through Payload's built-in jobs queue. Hooks stay pure; only task handlers touch the chain or populate `chain.*` mirror fields. This is what lets the webapp deploy on serverless platforms like Vercel — chain calls regularly exceed a serverless function's execution timeout, so a synchronous server action would time out and orphan on-chain state.

### Trigger → enqueue → run

1. A thin server action in `src/actions/*.ts` validates permissions, then calls `payload.jobs.queue({ task: '<slug>', input, queue: 'default' })`.
2. Immediately after the response is sent, the same action calls `after(() => payload.jobs.run({ queue: 'default', limit: 1 }))` (from `next/server`) so the queued job drains in-process without blocking the UI. The action returns `{ jobId }` so the admin UI can poll.
3. A `vercel.json` cron hits `/api/payload-jobs/run` every 5 min as a safety net for any job whose `after()` context died before the run completed.

The run endpoint is access-guarded in `payload.config.ts → jobs.access.run`. It accepts either a logged-in admin/manager **or** a Vercel Cron request carrying `Authorization: Bearer $CRON_SECRET`; any other caller is rejected.

### Task handler contract

Every task file under `src/tasks/*.ts` follows the same shape, so adding the next one (`scheduleIntervention`, `publishIntervention`, etc.) is a mechanical replica of `registerArea.ts`:

1. Load the target row, short-circuit to the existing `chain.*` mirror if the row is already in the terminal state (idempotent retries).
2. Transition `lifecycleStatus` to the in-flight state via `payload.update` with `overrideAccess: true` and `req.context.skipLifecycleHooks: true` — the only sanctioned way around the form-level freeze and the `validateInterventionTransition` guard.
3. Build the SDK input, fetch an `OpenGardenContext` from `lib/openGardenClient.ts`, and call the SDK method.
4. On success, populate the row's `chain.*` mirror + flip to the terminal state, then append a `chainTransactions` audit row via `lib/recordChainTransaction.ts`.
5. On error, flip to `failed`, append a failed audit row, and rethrow so Payload's retry machinery picks it up. Retries use `shouldRestore: true` (the default), so a previously-succeeded task inside a retried job is skipped.

No hooks call the SDK, no hooks touch `chain.*`. If you find yourself wanting to do either, you're in the wrong layer — write a task instead.

### Autorun vs cron

`jobs.autoRun` in `payload.config.ts` is gated on `ENABLE_PAYLOAD_AUTORUN=true`. Leave it unset in production (autoRun requires a persistent process, which serverless functions don't have). Set it for local dev if you want queued jobs to drain automatically without manually hitting the run endpoint.

## Deferred

The following are intentionally not in this package yet:

- Admin UI action buttons on each relevant edit view (`Schedule`, `Validate`, `Publish`, `Register Area`, `Build / Verify Bundle`). The `registerAreaAction` server action already exists; wiring a React button that calls it is the next step.
- Task handlers for the intervention state machine (`scheduleIntervention`, `validateIntervention`, `publishIntervention`) and evidence bundles (`buildBundle`, `publishBundle`, `verifyBundle`). Each follows the same shape as `registerArea.ts`.
- **Switching from the local SQLite file adapter to Postgres / Turso before the first Vercel deploy.** Vercel's filesystem is ephemeral and per-function, so `file:./webapp.db` cannot survive there — the jobs collection needs a shared, persistent datastore.
- Composite and partial-unique indexes (`sponsors.canonicalJson` for non-volunteer, `gardeners.wallet` for non-null, the `(intervention, gardener)` checkin uniqueness, etc.) — currently enforced at the application level via hooks. The DB-level partial indexes need a hand-edited migration file.
- IPFS pin pipeline beyond the stub `inMemory` storage adapter.
- `gardenerMilestones` and `citizenFeedback` collections.
- Impact dashboards.
